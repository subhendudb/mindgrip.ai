Overview

Project Description & Defined Outcome

Binary sort use case on the SO-101 dual-arm kit — learned from human demonstration, not hand-coded paths.

Problem statement

Manual sorting of match-box vs non–match-box items is repetitive and hard to scale in lab / light-industrial settings.

Primary use case

Match-box objects → match-box bin
All other objects → reject bin

Core challenge

Visually tell match-box from other objects; grasp and place into the correct of two bins; learn from human teleop demos.

Constraints

Limited kit docs & fragile 3D-printed parts; need vision + teleop data pipeline; bridge teleop → dataset → ACT → real-robot eval.

Approach

  1. Assemble & calibrate leader / follower arms
  2. Teleoperate demos with USB camera
  3. Record ~40–50 episodes per class (~80–100 total, balanced match-box / other)
  4. Train ACT (imitation learning / BC)
  5. Deploy & evaluate on the physical follower

Success criteria

  • Calibrated dual-arm teleop with USB camera
  • ~80–100 balanced demos (both object types)
  • Trained ACT policy deployed on follower
  • Autonomous correct-bin placement

Deliverables

  • Reproducible CLI / LeLab workflow
  • Dataset + ACT checkpoint
  • Demo video of autonomous sorting

Purpose

What This Project Builds

A tabletop SO-101 follower that learns to autonomously binary-sort match-box vs other objects into two bins — using USB-camera vision and joint actions from leader–follower teleop, then trained with ACT (imitation learning). The same pipeline later supports colour, shape, and other sorting scenarios.

🤖

Autonomous Manipulation

The SO-101 follower arm learns from human demonstrations to grasp, lift, and place objects into target zones without any manual control.

🧠

Imitation Learning Pipeline

Full ML pipeline: record human demos via leader-follower teleoperation → build a HuggingFace dataset → train a neural policy → deploy autonomously.

📷

Vision-Guided Sorting

A fixed USB camera streams an overview of the workspace. The policy maps pixels + joint states → motor commands to pick and sort with visual feedback.

🔬

Research & Education

Ideal for learning robotics, computer vision, and deep learning in one integrated project. Fully reproducible with open-source tooling.

Plan A — Standard laptop / desktop (8–16 GB) · recommended

Role of the host

Single machine for LeLab or CLI: calibrate, teleop with USB cam, record ~80–100 demos, push dataset, download ACT checkpoint, run rollout.

Training

Always offload Step 8 to HF Jobs (a10g-large) or AWS g5.xlarge / g5.2xlarge. 8 GB RAM is fine for control; 16 GB is more comfortable with LeLab + camera.

OS tips

Ubuntu: requirements-ubuntu.txt, ports like /dev/ttyUSB* / /dev/ttyACM*, add user to dialout. macOS: requirements-macos.txt, /dev/tty.usbmodem*, grant Camera permission.

When to choose this

Default for MindGrip AI. Best UX for beginners; supports full GUI and MuJoCo viewer (macOS/Linux desktop).

✅
Plan A workflow: record on laptop/desktop → push dataset to Hub → train ACT in cloud → pull checkpoint → rollout on the same host. Close browsers/IDEs while recording on 8 GB machines.

Plan B — Raspberry Pi 5 (8 GB) as primary host

Role of the Pi

Compact control PC next to the arm: Feetech USB serial + USB camera + CLI teleop/record/rollout. Prefer Pi 5 · 8 GB and a fast microSD (or NVMe if available).

What to skip on Pi

Local ACT training, heavy Rerun layouts, MuJoCo interactive viewer, and comfortable LeLab desktop use. Use CLI scripts / so101_cli_menu.sh patterns instead.

Camera & power

Use an official 27 W+ PSU for Pi 5. Prefer a powered USB hub for camera + two serial adapters. Record at 640×480; lower FPS if frames drop.

Training still in cloud

Same as Plan A: push dataset from Pi (or copy via USB/SCP), train on HF Jobs / AWS GPU, copy checkpoint back for Step 9 on the Pi.

⚠️
Pi 4: usable for motor setup and light teleop, but recording + ACT rollout is tighter (RAM + USB bandwidth). Prefer upgrading to Pi 5 8 GB or using Plan A for data collection.

Plan C — Hybrid (laptop + Raspberry Pi)

Best when you want a desktop GUI for setup but a small always-on box by the robot. The Pi owns the USB cables; the laptop is your console — not a remote USB bridge.

Architecture

Solution Control Flow

High-level algorithm design for the SO-101 binary sorter: an LfD loop with policy ACT, fallback teleop / replay, and a match-box vs reject decision tree. At every timestep the follower observes camera image I and joint state q; policy π maps that to an action chunk; servos execute; a success check continues or recovers.

🔁
LfD loop: teleop demos → train ACT → deploy π on follower · Fallback: leader teleop or episode replay · No classical RL and no online IK — demos encode both skill and bin routing.

👁

SENSE — (I, q)

I = USB camera image · q = joint state (shoulder, elbow, wrist, gripper). At teleop time this is logged as vision + proprioception; at deploy it is live frames + joint feedback.

🧠

CONTROL — π(a | I, q)

Policy outputs the next action (joint targets + gripper). Here π = trained ACT. Alternatives: leader teleop or open-loop replay (no live decision).

🦾

ACTUATE

Follower servos execute the action chunk — joints + gripper — on the physical SO-101.

✅

CHECK

Correct bin? NO → recover / re-grasp → back to SENSE. YES → next object, or END when the workspace is clear.

Motion phases inside CONTROL → ACTUATE

PhaseNameWhat happens
AApproachMove above / toward the object
BGraspClose gripper on the object
CTransportCarry toward the chosen bin
DPlaceRelease into match-box bin or reject bin
EHomeReturn to a ready pose for the next object

ACT policy — how autonomy is obtained

Action Chunking Transformers

Predicts a short chunk of future actions, not a single step. Trained by matching demo actions (often CVAE-style latent). Not classical RL — autonomy comes from cloning demos, then running π on the follower.

In one line

Model maps (I, q) → action chunks. Inverse kinematics is implicit in the demos — never solved online. See also FK / IK notes and policy cheatsheet.

Decision tree — match box vs non–match box

Binary sort · ACT learns both branches from teleop demos · no separate class tags — camera image + place action are the label. Target ~40–50 successful demos per branch (~80–100 total).

QuestionBranchAction / data
Object in workspace? (camera overview) NO END — workspace clear · episode done
Is it a yellow match box? (from image I) YES — match box Place in match-box bin (pose p_match) · ~40–50 demos
NO — other object Place in reject bin (pose p_reject) · ~40–50 demos
